# 週1レシート入力Web家計簿 要件定義

## 1. 概要

本アプリは、毎日家計簿をつけることが続かないユーザー向けに、週1回まとめてレシートを入力し、支出を振り返るためのWeb家計簿アプリである。

ブラウザで利用できるWebアプリとして提供し、PCとスマートフォンの両方で主要操作を完了できることを前提とする。銀行口座・クレジットカード連携や高精度OCRを前提にせず、手入力でも短時間で完了できる入力体験と、週単位の振り返りに重点を置く。

## 2. Product Lead判断

### 2.1 初期ポジショニング

本アプリは、資産管理アプリではなく、週次の支出棚卸しWebアプリとして設計する。

既存の高機能家計簿アプリと正面から競合しないため、MVPでは以下に集中する。

- 毎日入力しなくてもよい
- 週1回の入力作業を短く終えられる
- 今週の使いすぎに気づける

### 2.2 MVPで検証する仮説

- ユーザーは毎日ではなく週1回なら家計簿入力を続けやすい
- レシート入力が手入力でも、入力項目が少なければ許容される
- 週次のカテゴリ別集計と振り返りがあれば、詳細な資産管理がなくても価値を感じる
- Webアプリでも、スマートフォンで入力しやすければ日常利用に耐えられる

### 2.3 Webアプリとしての初期決定

| 項目         | 初期決定                                  | 理由                                                                                               |
| ------------ | ----------------------------------------- | -------------------------------------------------------------------------------------------------- |
| 提供形態     | Webアプリ                                 | インストール不要で試しやすく、PCとスマートフォンの両方で使えるため                                 |
| 対象端末     | PC、スマートフォン、タブレット            | 週末のまとめ入力はPC、レシートを見ながらの軽い入力はスマートフォンでも起こり得るため               |
| 初期保存方式 | クラウドDB保存                            | 複数端末で同じ家計データを同期するため                                                             |
| 認証         | Clerk + Googleアカウント認証をMVPから利用 | クラウド同期ではユーザーごとのデータ分離が必須であり、Google認証なら初回利用の負担を抑えやすいため |
| 同期方式     | Convexを第一候補                          | Reactから扱いやすく、クエリがリアクティブに同期されるため                                          |
| 週の開始日   | 月曜日                                    | 週次振り返りと相性がよく、日本の生活感覚にも合いやすいため                                         |
| 通貨         | 日本円                                    | 初期ターゲットを日本在住ユーザーに置くため                                                         |
| 金額         | 税込合計のみ                              | 明細入力は負荷が高く、MVPの目的から外れるため                                                      |

## 3. コンセプト

- 毎日つけなくてよい家計簿
- 週1回、レシートを片付けるだけ
- 完璧な資産管理ではなく、続く支出の振り返りを支援する

## 4. 想定ユーザー

### 主要ユーザー

- レシートを財布や机に溜めがちな人
- 毎日家計簿をつける習慣が続かない人
- 銀行口座やクレジットカード連携に抵抗がある人
- スーパー、ドラッグストア、外食、現金支出を週単位で見直したい人

### 初期ターゲット

- 一人暮らし、または夫婦・同棲世帯のうち、まずは自分の支出を把握したいユーザー
- 月次の厳密な会計よりも、週次の使いすぎ確認を重視するユーザー

## 5. 解決する課題

- 毎日入力する家計簿は心理的負担が高く、継続しにくい
- 高機能な家計簿アプリは設定や連携が多く、始めるまでが重い
- レシートが溜まると、何にいくら使ったかを後から把握しづらい
- 月末まで振り返らないと、使いすぎに気づくのが遅い

## 6. MVPの目的

MVPでは、ユーザーが週1回まとめて入力し、その週の支出傾向を確認できる状態を目指す。

成功条件は、ユーザーが次の操作を迷わず完了できることである。

1. 今週の入力セッションを開始する
2. 複数枚のレシートを連続して入力する
3. カテゴリ別の週次支出を確認する
4. 必要に応じて設定を確認する

## 7. MVPスコープ

### 作る機能

- 週次入力セッション
- 支出の手入力（`expenseEntries` を正本。複数支出項目モード、合計金額と内訳の差額確認を含む）
- 収入の手入力（`expenseEntries.entryType: "income"` を正本とし、収入カテゴリは作らない）
- 店名・カテゴリの入力補助
- カテゴリ別集計
- レシート入力済みの進捗表示
- 基本的なカテゴリ管理
- 週の開始・終了曜日のユーザー設定保存
- ClerkによるGoogleアカウント認証
- 複数端末でのデータ同期
- 家族・グループ共有（複数グループ所属、オーナー/メンバー権限、Clerk経由のメール招待）
- 公開ページ（`/privacy`、`/terms`）とメンテナンスモード
- レシート画像から店名・日付・合計金額の候補を抽出する補助PoC
- AI支出下書きキュー（レシート/コンビニ払込票、確認が必要な下書き、まとめて登録）

### 作らない機能

- システム管理者 UI（設計のみ。`docs/system-admin-authorization.md` 参照）
- 銀行口座連携
- クレジットカード連携
- 高精度OCRを前提にした自動登録
- レシート明細行の自動確定登録
- サブスク管理
- 資産管理
- 投資管理
- 複雑な予算ルール
- スマートフォンネイティブアプリ
- デスクトップネイティブアプリ
- オフラインファーストの高度な同期
- CSVエクスポートUI（現行コードでは未実装。将来のバックアップ導線として扱う）

## 8. 主要画面

### 8.1 ダッシュボード

目的: 今週の支出状況と入力状態をすぐ確認する。

表示項目:

- 今週の合計支出
- 今週の合計収入
- カテゴリ別支出
- 今週の入力済み件数（`expenseEntries` ベース）
- 前週比

セッション状態（未開始 / 入力中 / 完了）は独立表示せず、主要操作ボタンの文言（「今週の入力を開始」「入力を再開」「週次サマリーを見る」）に内包する。

主要操作:

- 今週の入力を開始する
- 入力中セッションを再開する
- 週次サマリーを見る

### 8.2 週次入力画面

目的: 週1回、複数枚のレシートを連続して入力する。

入力項目:

- 日付（週内の曜日選択 UI）
- 店舗名 / 支払先
- 合計金額
- カテゴリ（単一項目モード、または複数支出項目モード）
- メモ（任意）

入力補助:

- 過去に入力した店名候補
- 店名に紐づくカテゴリ候補
- 直近で使ったカテゴリ候補
- 「カテゴリ別の内訳を追加」から開く複数支出項目モード（内訳合計と合計金額の差額確認ダイアログ）
- 入力後に続けて次のレシートを追加する導線
- AI支出下書きキュー（`AiExpenseQueuePanel`、見出し「レシート入力」）による一括登録

### 8.3 週次サマリー画面

目的: その週の支出を確認し、次週に活かす。

表示項目:

- 合計支出
- 合計収入（合計支出の直下）
- カテゴリ別支出
- 前週比
- **週別支出推移（対象週を含む直近3週間の棒グラフ）**
- 支出一覧（各項目にメモがある場合は表示。長文は「もっと見る」で展開）
- 収入一覧（支出一覧と同様の行形式。カテゴリ列なし。5件超は展開）

主要操作:

- 支出を修正する
- グラフの棒をホバーまたはタップして週ごとの比較を見る

### 8.4 設定画面

目的: ユーザーが自分の生活に合わせてカテゴリと週設定を管理する。

初期カテゴリ:

- 食費
- 日用品
- 外食
- 交通
- 医療
- 娯楽
- 衣服
- その他

主要操作:

- カテゴリを追加する
- カテゴリ名を変更する
- カテゴリを無効化する
- 週の開始曜日・終了曜日を保存する
- グループを作成する
- 複数所属時に表示対象グループを切り替える
- オーナーがメンバーを招待・削除する

現行実装では `/settings` にグループ管理、カテゴリ設定、週の設定をまとめて表示する。`/categories` は同じ設定画面への互換ルートとして扱う。

### 8.5 エクスポート画面

目的: 入力データを外部で利用できるようにする。

現行コードでは `/export` 画面とCSV生成処理は未実装である。将来のバックアップ導線として要件を残す。

出力形式:

- CSV

出力項目:

- 日付
- 店名
- 金額
- カテゴリ
- メモ
- 週開始日
- 週終了日

## 9. Webアプリ要件

### 9.1 対応環境

- モダンブラウザで動作すること
- PC幅、タブレット幅、スマートフォン幅で主要操作を完了できること
- 初期MVPではネイティブアプリ化を行わない
- PWA対応は将来拡張とする

### 9.2 レスポンシブ方針

- PCでは、週ナビゲーションと入力フォームを読みやすい幅で配置する
- スマートフォンでは、1画面1タスクを基本にして、連続入力を妨げない
- 主要ボタンはタップ操作しやすいサイズにする
- 表形式の情報はスマートフォンで横スクロール前提にせず、カードまたは縦積み表示に切り替える

### 9.3 保存とデータ保護

- MVPではクラウドDBに家計データを保存する
- グループごとのデータ分離を必須とする
- 認証していないユーザーは家計データを作成、閲覧、更新、削除できない
- CSVエクスポートは現行コードでは未実装であり、将来ユーザーが自分でバックアップできる手段として検討する
- オフライン入力はMVPでは必須にしない

### 9.4 入力体験

- レシートを見ながら片手でも入力しやすいフォームにする
- 保存後は次のレシート入力にすぐ進める
- 日付やカテゴリは直前入力の値を活用し、同じ操作の繰り返しを減らす
- キーボード操作でも連続入力しやすいこと

### 10.5 Group / GroupMember

家計データの共有単位はグループである。ユーザーは複数グループに所属でき、ログイン後に表示対象のグループを選択または切り替えられる。

| 項目          | 型       | 必須 | 説明                                      |
| ------------- | -------- | ---: | ----------------------------------------- |
| groupId       | string   |  yes | 家計データの所有境界となるグループID      |
| name          | string   |  yes | グループ名                                |
| role          | string   |  yes | `owner` / `member`                        |
| activeGroupId | string   |   no | ユーザーが現在表示対象にしているグループID |

オーナーはClerk invitationを経由して招待メールを送信し、招待を受け入れたユーザーは対象グループの `groupMembers` に追加される。メンバー削除は `groupMembers` からの削除であり、Clerkアカウントや `users` レコードは削除しない。

### 10.6 AI支出下書き

画像解析結果は `receipts` に直接保存せず、`aiExpenseDrafts` と `aiExpenseDraftItems` に下書きとして保存する。

- `aiExpenseDrafts`: 書類種別、解析状態、支払先/支払場所/支払内容、候補日付、金額、税率別集計（`taxSummaries`）、カテゴリ、信頼度、確認理由を持つ。`registeredReceiptId` はレガシー互換用で、主導線では未使用。
- `aiExpenseDraftItems`: 親下書きに紐づく明細行を別テーブルで持つ。印字額、税込・税抜（`amountBasis`）、税率、按分税、正規化登録額（`normalizedAmountYen`）を保持する。
- 対応する書類種別は `receipt`、`convenience_payment`、`unknown`。
- 状態は `queued`、`analyzing`、`ready`、`needs_review`、`failed`、`registered`。
- 登録時は ready 下書きを `expenseEntries` に変換し（`registerReadyDraftsAsExpenseEntries`）、下書きを `registered` に更新する。
- 商品明細はレシートに印字された行金額（`printedAmountYen`）を保持し、登録は正規化した税込額（`normalizedAmountYen`）とする。税額集計行は明細として登録しない。
- 外税・内税・税率不明は正規化処理で登録額を算出し、確認不能な場合は警告として下書き確認画面に表示する。
- 手入力 MVP の「税込合計のみ」方針（§2.3）とは別に、AI 解析では明細レベルで税情報を扱う。
- 画像解析時は現在有効なカテゴリ名をOpenAIへ候補として渡し、下書き全体と各商品明細のカテゴリ名を候補内から返させる。
- 画像解析で作成した下書きは単一・複数カテゴリを問わず確認必須とし、確認後に登録準備OKへ移動する。
- 支出日は画像の読込日・登録日ではなく、レシートまたは払込票に記載された日付を初期値としてユーザーが確定する。
- 値引き明細は下書き内で負数として保持し、対象カテゴリの正額明細と合算した正味額を正の `expenseEntries` として登録する。
- 通常はレシート全体のカテゴリを全商品へ適用し、複数カテゴリの場合は明細ごとにカテゴリ変更を可能にする。
- 2カテゴリ以上に分類されたレシートは自動登録せず確認を必須とし、カテゴリ別登録候補の確認後に登録する。
- 値引き対象が不明な場合は対象商品を選択して同じカテゴリから減額する。明細合計と支払合計が不一致の場合と同様に自動按分せず確認を必須にする。

### 10.7 M18. 入力元と支出項目の分離方針

M18では、週1回まとめ入力する既存MVP利用者を対象に、レシート、払込票、手入力、AI下書きなどの「入力元」と、カテゴリ別に集計・振り返りする「支出項目」を分離して扱う。

当面の正本は次のように整理する。

- `sourceDocuments`
  - schema 上の正本名とする
  - 何を、どの経路で、どの時点で入力したかを表す
  - レシート、払込票、手入力、AI下書きなどの入力元を保持する
- `inputSources`
  - 説明文やUIで使う言い換えとして扱う
  - 意味は `sourceDocuments` と同じ
- `expenseEntries`
  - カテゴリ別支出項目を表す
  - 「何に、いくら、どのカテゴリとして記録したか」を表す
  - 1つの入力元から複数の支出項目を作れる前提を持つ

schema（`sourceDocuments`、`expenseEntries`、`receiptAnalysisBatches`、`receiptAnalysisImageJobs`）は実装済みである。

現行の移行状況:

1. schema と用語の確定 — **完了**
2. 既存 `receipts` との互換・移行方針の確定 — **完了**（`convex/receipts/spendingEntries.ts`）
3. 週次集計とサマリーの `expenseEntries` 寄せ — **完了**（`convex/receipts/spendingEntries.ts`）
4. 入力元から複数の支出項目を作る UI — **完了**（`ExpenseEntryForm` の複数支出項目モード）
5. AI下書きから支出項目候補を作る導線の整理 — **完了**（`registerReadyDraftsAsExpenseEntries`）

`receipts` は互換層として残し、手入力・AI 登録の正本は `expenseEntries` である。

### 10.8 SystemAdmin

システム管理者権限は `groupMembers.role` と分離し、Convex の `systemAdmins` を正本とする設計である。
MVP は active な `admin` のみを扱い、家計データへの横断アクセス権は付与しない。

**現行コードでは `systemAdmins` テーブル、関連 API、`/admin` UI は未実装**である。
設計の正本は `docs/system-admin-authorization.md` を参照する。

## 11. ユーザーストーリー

- ユーザーとして、今週のレシート入力を開始したい。そうすることで、溜まったレシートをまとめて処理できる。
- ユーザーとして、店名と金額だけで素早く支出を登録したい。そうすることで、入力の負担を減らせる。
- ユーザーとして、前回使った店名やカテゴリを候補表示してほしい。そうすることで、同じ入力を繰り返さずに済む。
- ユーザーとして、1 枚のレシートから複数カテゴリの支出項目を入力したい。そうすることで、内訳を正確に記録できる。
- ユーザーとして、カテゴリ別に今週の支出を見たい。そうすることで、何に使いすぎたかを把握できる。
- ユーザーとして、レシート画像から候補を作りたい。そうすることで、手入力の負担を減らせる。
- ユーザーとして、AI下書きを確認してまとめて登録したい。そうすることで、入力作業を短くできる。
- ユーザーとして、入力データをCSVで出力したい。そうすることで、表計算ソフトなどで再利用できる（現行UIでは未実装）。

## 12. 受け入れ条件

### 12.1 週次入力セッション

- ユーザーは現在週の入力セッションを作成できる
- 既に現在週のセッションがある場合は、そのセッションを再開できる
- セッションには週開始日と週終了日が設定される

### 12.2 支出入力

- ユーザーは日付、店舗名/支払先、金額、カテゴリを入力して支出を `expenseEntries` に保存できる
- 複数支出項目モードでは、内訳合計と合計金額の差額を確認してから保存できる
- 保存成功時に「支出項目を保存しました」と表示される
- 入力画面で支出と収入を切り替え、収入は日付・金額・内容で保存できる
- 収入ではレシート操作、店舗、支出カテゴリ、カテゴリ別内訳を表示しない
- 金額が0以下の場合は保存できない
- 必須項目が未入力の場合は保存できない
- 保存後、続けて次のレシートを入力できる

### 12.3 集計

- ダッシュボードに今週の合計支出が表示される
- ダッシュボードに今週の合計収入が表示される（Issue #395）
- カテゴリ別の合計金額が表示される
- **週次サマリー画面に対象週を含む直近3週間の支出合計が棒グラフで表示される**
- **棒グラフの金額軸が円・万円の理解しやすい表記で、画面幅にかかわらず見切れず表示される**
- **グラフ上部に対象週の支出、前週差、直前2週間の平均比が表示される**
- **同じ指標パネル内の合計支出の下に、対象週の合計収入が表示される（Issue #378）**
- **収入一覧に入力済みの収入が表示される（Issue #378）**
- **棒のTooltipで週範囲と支出合計を確認できる**
- **直前2週間の支出がともに0円の場合、平均比は比較データなしと表示される**
- 予算金額や予算残額は表示しない

### 12.4 振り返り

現行UIでは振り返りメモと週次セッション完了操作を表示しない。既存データとの互換性を保つため、
保存済みの `reviewMemo` とセッション状態は削除しない。

### 12.5 CSVエクスポート

現行コードでは未実装。将来実装時の受け入れ条件は次のとおり。

- ユーザーは指定した週の支出をCSVで出力できる
- CSVには日付、店名、金額、カテゴリ、メモ、週開始日、週終了日が含まれる

## 13. 非機能要件

### 13.1 操作性

- スマートフォン幅でも主要操作を完了できる
- レシートを連続入力しやすい画面構成にする
- 入力フォームは項目数を最小限にする
- PCではキーボード中心、スマートフォンではタップ中心の操作に対応する

### 13.2 パフォーマンス

- ダッシュボードの初期表示は体感で遅くならないこと
- 週次集計は保存済みデータから即時表示できること

### 13.3 データ保護

- 家計データは個人情報に準ずる情報として扱う
- 家計データは認証済みユーザーが所属するグループ内だけで扱えること
- サーバー側のquery/mutationで認証ユーザーの `groupMembers` 所属を確認し、他グループのデータへアクセスできないこと
- CSVエクスポートを将来実装する場合は、ユーザーが所属グループのデータだけを出力できること

### 13.4 保守性

- レシート、週次セッション、カテゴリを分離して管理する
- 将来的な画像解析、AI登録、複数グループ運用に備え、MVPでは依存しすぎない構造にする

## 14. 成功指標

MVP検証では、以下を成功指標とする。

- 初回ユーザーが5分以内に最初の週次入力とサマリー確認を完了できる
- 1セッションで5枚以上のレシートを連続入力できる
- ユーザーが週次支出のカテゴリ別傾向を理解できる
- 翌週も入力したいと思える導線になっている
- スマートフォン幅でも、レシート登録から週次サマリー確認まで完了できる

## 17. レシート画像入力PoC方針

M11「レシート画像入力PoC」では、手入力を主導線にしたまま、画像から店名・日付・合計金額の候補を抽出する補助機能を扱う。

### 17.1 外部API送信

- 初回実装では、Convex Action から OpenAI Vision 対応 API へ画像を送信する方式を許容する。
- ユーザーが初めて画像読み取りを実行する前に、外部API送信への同意ダイアログを表示する。
- 同意がない状態では、画像データを外部APIへ送信しない。
- 同意済み状態はユーザー単位で Convex に保存し、次回以降の読み取り判定に使う。

### 17.2 画像保存と保持期間

- 初回PoCでは、レシート画像を長期保存しない。
- 画像はブラウザ上の一時プレビューと、解析リクエスト用の一時データとしてのみ扱う。
- Convex Storage に画像を保存しない。
- 監査や改善用の永続ログを追加する場合も、画像そのものは保存対象にしない。

### 17.3 ユーザー向け説明文

画像読み取り導線では、次の内容を短く説明する。

- 読み取り時はレシート画像を外部APIへ送信する。
- 画像は長期保存しない。
- 読み取った店名・日付・金額は候補としてフォームに反映される。
- 抽出結果は自動保存されず、ユーザーが確認・修正してから通常の保存操作を行う。
- 同意しない場合や読み取りに失敗した場合も、手入力を継続できる。

### 17.4 保存フロー

- 抽出結果は receipt として自動保存しない。
- 既存の `保存して次へ` を押したときだけ、通常のレシート保存処理を行う。
- 失敗時、低信頼度、読み取り不能、または同意拒否時は、同じ入力フォームで手入力へ戻れることを必須とする。
