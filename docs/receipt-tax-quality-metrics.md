# レシート税判定の品質指標

Issue #674 の品質指標契約。税判定の安全性を確認するための指標を、
「現在の決定的なオフライン評価」と「将来、本番計測を追加する場合の契約」に分けて定義する。

## 決定事項

- 現在のリポジトリには安全な本番分析イベント基盤がないため、本Issueではイベント送信・新規分析サービス・Convexの計測用schemaを追加しない。
- 既定の評価方法は、`lib/domain/receipt/tax/fixtures/receiptTaxGoldenCaseLedger.ts` を入力にした決定的テストとする。外部AI、実画像、OCR原文の外部送信は行わない。
- `sourceAvailability: "unavailable"` のケースは成功・失敗の分母へ入れず、資料不足として別に報告する。資料不足を0件や正常として扱わない。
- 「誤警告率」は真の正解率ではない。人手で確認されたground truthがない期間は、警告後に変更されなかった割合を代理指標として表示し、正解率と混同しない。
- 本番イベントを有効化する場合は、収集先・保持期間・送信項目を別の実装Issueで定義し、プライバシー確認を通過してから行う。

## 1. 指標の定義

### 1.1 本番計測候補（現在は未有効化）

| ID | 指標 | 分母 | 分子 | 除外条件 | 解釈 |
| --- | --- | --- | --- | --- | --- |
| QT01 | 税解釈の手動補正率 | 税解釈を表示し、保存操作まで到達したレビューセッション | 初期候補から税率・価格表示・税額・明細等を1項目以上ユーザーが変更したセッション | キャンセル、表示前の解析失敗、重複イベント、テストユーザー | ユーザーが補正を必要とした割合。正誤率ではない |
| QT02 | レシート合計の手動補正率 | 支払総額候補を表示して保存操作まで到達したセッション | 初期候補と異なる合計をユーザーが確定したセッション | 合計候補なし、キャンセル、重複イベント | 合計保護のために補正された割合 |
| QT03 | 合計だけ保存率 | 保存モードを選択して登録に成功したセッション | `totalOnly` で登録に成功したセッション | 登録失敗のみの試行、離脱、同一登録の再送 | 税内訳を確定せず合計だけ保存した割合 |
| QT04 | 警告表示率 | レビュー画面の表示まで到達したセッション | 税・合計・明細に1つ以上の警告を表示したセッション | 表示前の解析失敗、重複イベント | 問題候補が提示された割合 |
| QT05 | 警告後未変更保存率（代理指標） | 警告を表示したセッション | 警告対象を変更せず保存に成功したセッション | キャンセル、登録失敗、重複イベント | 誤警告の代理。真の誤警告率とは報告を分ける |
| QT06 | 登録失敗後の再試行率 | 登録操作を開始したセッション | 初回登録が失敗し、同じレビュー内容で再試行したセッション | イベント欠落が確認できないセッション、重複イベント | 失敗経路の発生割合 |
| QT07 | 二重登録率 | 登録に成功したセッション | 1セッションから同じ下書きに対して2件以上の支出が生成されたセッション | テスト・fixture、意図した複数明細 | 金融安全指標。目標は常に0 |
| QT08 | 指標イベント送信失敗率 | 送信を試みた指標イベント | 送信に失敗したイベント | 計測を無効化した期間、重複イベント | 登録処理とは別に監視する。送信失敗で登録を失敗させない |
| QT09 | 指標イベント重複率 | 受信したイベント | 同じidempotency keyを重複して受信したイベント | 無効なイベント、テストイベント | 再送時に1回だけ集計できているかを確認する |

QT01・QT02の「変更」は、クライアントの表示状態だけでなく、保存時に確定した値と対応付けて判定する。
セッション識別子やidempotency keyを導入する場合も、ユーザーID・グループID・家計金額を計測キーにしない。

### 1.2 オフライン評価指標

`receiptTaxGoldenCaseLedger` の同じrevisionを使い、実行日時・commit SHA・台帳の件数を記録する。

| ID | 指標 | 分母 | 分子 | 除外 / 注意 |
| --- | --- | --- | --- | --- |
| OFF01 | ケース資料利用可能率 | R001〜R038の全ケース | `approved_image` または `anonymized_lines` のケース | `unavailable` は不足資料として別掲 |
| OFF02 | ground truth確認率 | 利用可能ケース | `groundTruthReviewed: true` のケース | 未確認を不正解や正常として数えない |
| OFF03 | OCR文字誤りケース網羅率 | ground truth確認済みケース | `ocr_character_error` を持つケース | 網羅率であり、OCR精度ではない |
| OFF04 | 意味誤割り当てケース網羅率 | ground truth確認済みケース | `semantic_misassignment` を持つケース | OCR文字誤りと別集計する |
| OFF05 | 期待警告ケース率 | ground truth確認済みケース | `expected.warningCodes` が1件以上のケース | 誤警告率ではなく、決定的な警告提示対象の割合 |
| OFF06 | totalOnlyシナリオ率 | ground truth確認済みケース | `expected.registrationMode == "totalOnly"` のケース | ユーザーの本番選択率ではない |
| OFF07 | 決定的期待値不一致率 | `input` があり、外部AIなしで評価できるケース | 解釈結果が台帳の期待値と一致しないケース | テスト失敗は0を要求する。資料不足ケースは分母外 |

## 3. 改善前後の比較方法

1. 指標ID、式、除外条件、台帳・コードのcommit SHAを変更前に固定する。式を変えた場合は新しい指標versionとして扱い、旧versionと直接比較しない。
2. オフライン評価は同じR001〜R038のCase IDと同じ検証コマンドで実行し、`available`、`groundTruthReviewed`、`unavailable` を併記する。
3. 本番計測を将来追加する場合は、同じイベント定義を使った期間を「変更前」「変更後」に分け、各期間の分子・分母・除外件数・欠測件数を併記する。分母が0の指標は0%ではなく `N/A` とする。
4. 代理指標（QT05）と、ground truthを用いたオフラインの期待値不一致（OFF07）は別表にし、代理指標の改善を正解率の改善と表現しない。
5. 期間・環境・コードrevision・指標versionを揃えられない比較は「比較不能」として残す。

## 4. 停止・切り戻し基準

次のいずれかに該当した場合は、計測のために登録経路を変更せず、まず計測送信を無効化して原因を確認する。

- 画像、OCR原文、商品名、金額、店舗名、ユーザー/グループ識別子、secretがイベント・ログ・分析保存先へ含まれた。
- OFF07が1件でも0を外れた、またはQT07（二重登録）が1件でも発生した。
- ユーザー確認済みの支払総額が変わる、税行・決済行が商品へ混入するなど、#665の金融不変条件に反する事象が確認された。
- イベント送信の失敗や重複が、レシート登録の成功・再試行・補正値保持を妨げた。

警告後未変更保存率（QT05）が、同じ指標version・同じ除外条件で比較した基準期間より10ポイント以上悪化し、
各週30セッション以上で2週連続した場合は、誤警告の代理悪化としてレビューを開始する。これは自動的な本番データ変更ではなく、
計測を止めて#672の決定的テストと代表E2Eを再確認するための停止基準や。

切り戻しは、(1) 計測送信のfeature flagを無効化、(2) 登録経路が計測なしで成功することを確認、
(3) 必要なら直前のpreview/mainの実装へ戻す、の順に行う。本番データを一括修正したり、削除したりする手順はこのIssueへ追加しない。

## 5. プライバシーと将来イベントの契約

### 現在

- 本番イベント送信は未実装・未有効化。したがって「送信失敗が登録を妨げない」実行経路も現在は存在しない。
- #672のfixtureテストは画像拡張子、画像URL、OCR原文の識別情報、メール、token形式、長いカード番号等の混入を検査する。
- オフラインのbaselineは匿名Case ID、失敗分類、状態enum、件数だけを出力し、実レシートとの対応表を持たない。

### 将来の別Issueで必須にする契約

- 計測payloadは、version付きの指標ID、許可された状態enum、環境、発生時刻の粗いbucket、ランダムな送信idempotency keyだけに限定する。画像、OCR原文、商品名、金額、店舗名、認証・グループ識別子を送らない。
- 送信はbest-effortとし、送信失敗はwarning/監視へ分離して登録mutationの結果やユーザー入力を変更しない。
- 同じidempotency keyの再送は受信側で1回だけ集計する。タイムアウト後の再試行、重複受信、部分成功を決定的テストで検証する。
- 収集先、保持期間、アクセス権限、削除手順、secretの扱いを実装前に明記し、プライバシー確認を通過するまで本番送信を有効にしない。

この契約だけではイベント送信を実装したことにならない。実装する場合は、送信失敗・重複・登録独立性を含む別Issue/PRで扱う。

## 6. 検証と更新手順

現行のbaselineを再計算する場合は、次の決定的テストを実行する。

```bash
pnpm exec vitest run lib/domain/receipt/tax/receiptTaxGoldenCases.test.ts
pnpm exec vitest run lib/convex/aiExpenseDrafts/receiptTaxGoldenRegistration.test.ts
pnpm run lint
pnpm run format:check
pnpm run build
```

台帳や指標式を変更したPRでは、表のcommit SHA・件数・未利用ケース・残余リスクを同じPR本文へ更新する。
外部AI評価や実画像評価を通常CIへ追加しない。
