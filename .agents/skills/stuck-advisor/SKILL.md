# Stuck Advisor

ハマったとき専用の「別視点アドバイザー」Skill。
経験豊富なシニアエンジニアとして、**今の方針を一度手放して**状況を構造化し、
別アプローチの仮説を提示する。

## Codex / Devin 共通の委譲ルール

- Codexでは、ユーザーが「必要に応じてサブエージェントを起動してよい」と明示した場合、それを単なる許可ではなく、同じ問題で2回以上失敗した局面で別視点アドバイザー起動を要求する指示として扱う。
- Codexでサブエージェント機能が未ロードなら、まず `tool_search` で multi-agent / spawn 系ツールを探す。`multi_agent_v1.spawn_agent` が使える場合は、`別視点アドバイザー サブエージェントを起動` という名前をプロンプトに含め、`agent_type: code_explorer` または `explorer` で起動する。
- CodexでこのSkillの自動トリガー条件を満たす場合は、次のアクションを決める前に、メインエージェントだけで代替せず実行時サブエージェントを起動する。
- Devinでは、同じ指示を別視点担当または内部タスク分割への委譲許可として扱う。
- サブエージェントへ委譲する場合は、ハマっている症状、試したこと、失敗回数、関連ファイル、実行したコマンドを渡す。
- サブエージェントは調査・仮説提示を担当し、許可された担当範囲外の修正や破壊的操作をしない。
- 実行時サブエージェントが利用できない環境では、利用できない理由を明記してから、メインエージェントがこのSkillを使って同じ観点で状況を整理する。

## いつ呼ぶか（自動トリガー条件）

次のいずれかに該当したら、ユーザー確認へ進む前に `stuck-advisor` を invoke すること。

| 状況 | 条件 |
|------|------|
| E2E失敗→修正ループ | 同じE2Eテストが2回以上失敗した |
| 実装↔レビュー差し戻しループ | 同じ指摘で2回以上差し戻された |
| ローカル確認ループ | 同じコマンド・手順を2回試して同じ結果になった |
| 任意 | Codex / Devin自身が「同じ方向を繰り返している」と感じたとき |

issue-delivery 中は、ここで状況を整理してから、継続・分割・別アプローチ・ユーザー確認のどれに進むかを決める。

## ステップ1: 状況の構造化（5W1Hで整理する）

次のフォーマットで現状を整理すること。**「たぶんこれが原因」という思い込みを一度排除して**事実だけを書く。

```
## 状況整理

### 何をしようとしているか（What）
- （例）E2Eテスト「ボタンをクリックするとパネルが表示される」を通す

### 何が起きているか（実際の症状）
- （例）`toBeVisible()` が失敗する。エラーメッセージ: ...

### 試したこと（順番に）
1. （例）Collapse の unmountOnExit を追加した → 変わらず失敗
2. （例）locator を getByRole に変更した → 変わらず失敗

### 試していないこと・まだ確認していないこと
- （例）テスト対象のコンポーネントが実際にマウントされているか確認していない
- （例）Vite devサーバーのキャッシュが残っている可能性を確認していない

### 最後に「成功」した状態（あれば）
- （例）コミット XXX の時点ではテストが通っていた
```

---

## ステップ2: シニアエンジニアの「まずここを疑う」チェックリスト

状況を整理したら、次の観点で見直す。**自分が固執していたアプローチとは関係なく**、一つずつ確認する。

### テスト・E2E系の問題でよく見落とすこと

- [ ] テストが実際に**正しいDOM要素**を対象にしているか？（隠れた要素・別のコンポーネントのコピーにヒットしていないか）
- [ ] **非同期・待機**が適切か？（`await`漏れ、`waitFor` なしで即アサート）
- [ ] テスト環境と本番環境で**データ状態**が違わないか？（DB に古いデータが残っている等）
- [ ] テストコードと実装コードの**どちらに問題があるか**を切り分けたか？
- [ ] ブラウザの**キャッシュ・ビルドアーティファクト**をクリアしたか？
- [ ] CI と ローカルで環境変数・シークレット・Convex接続先が違わないか？

### 実装系の問題でよく見落とすこと

- [ ] 問題が**自分が触ったファイルの外**にある可能性を検討したか？
- [ ] 型エラー・ランタイムエラーが**コンソールに出ていないか**確認したか？
- [ ] **副作用・グローバル状態**が干渉していないか？（テスト間、コンポーネント間）
- [ ] 「動くと思っていた部分」が**実は前提から崩れていた**可能性はないか？

---

## ステップ3: 別アプローチ仮説を3つ生成する

ステップ1・2を踏まえて、**今の方針とは独立した**アプローチを3つ提示する。

フォーマット:

```
## 別アプローチ仮説

### 仮説A: （タイトル）
- 根拠: なぜこのアプローチが有効か
- 手順: 具体的に何をするか（1〜3ステップ）
- リスク・注意点: この方向が外れる可能性と判断基準

### 仮説B: （タイトル）
- 根拠: ...
- 手順: ...
- リスク・注意点: ...

### 仮説C: 問題の定義を見直す
- 根拠: 「解こうとしている問題自体が本当の問題か」を疑う
- 手順: もっとシンプルな方法で同じゴールを達成できないか検討する
- リスク・注意点: ...
```

---

## ステップ4: 次のアクションを1つだけ決める

仮説A・B・Cの中から、**最もリスクが低く検証が速い1つ**を選んで実行する。

- 検証に5分以内で結果が出る仮説を優先する。
- 大きな変更を伴う仮説は後回しにする。
- 選んだ仮説が外れたら、次の仮説に移る（同じ仮説を繰り返さない）。

---

## 注意

- このSkillはCodex / Devinに「答え」を与えるものではなく、**思考をリセットするトリガー**である。
- ステップ1〜4を実行した上で、それでも解決の糸口が見えない場合は **打ち切り条件** に従いユーザーへエスカレーションする。
